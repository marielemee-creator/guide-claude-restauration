Pourquoi créer un projet plutôt qu’un chat isolé ?

Le projet devient la maison du sujet. On y garde le contexte durable ; chaque nouvelle conversation peut alors traiter une tâche précise sans tout mélanger.

Projet dans Claude

Créez un espace « Opérations restaurants », ajoutez les documents de référence et les instructions communes, puis ouvrez un chat différent pour chaque analyse. Une information n’est réutilisée entre les chats que si elle figure dans les connaissances ou instructions du projet.

Projet dans Claude Code ou Codex

Ouvrez un dossier dédié à l’outil. Il contient les fichiers, les règles CLAUDE.md ou AGENTS.md, les tests et l’historique Git. L’agent peut reprendre le travail là où il s’est arrêté.

Un sujet = un projet · des règles stables · moins de fichiers oubliés · retour en arrière possible · transmission plus simple

01Créer le projet et son dépôt GitHub

Vous n’avez pas besoin de taper les commandes ci-dessous. Ouvrez le dossier dans Claude Code ou Codex et dites : « Initialise Git proprement, crée le dépôt GitHub en privé et explique-moi chaque validation. » L’agent ajoutera d’abord un .gitignore et un .env.example.

Ce que l’agent fera en arrière-plan :

git init
git add .
git commit -m "Initial project"
git branch -M main
git remote add origin https://github.com/organisation/projet.git
git push -u origin main
Avant le premier git add . : vérifier qu’aucun mot de passe, fichier .env ou export réel n’est présent. Après chaque évolution : git status, git diff, commit clair, git push, puis contrôle sur GitHub et sur le site publié.
02Mettre les bons fichiers à la racine 
README.md
AGENTS.md          # Codex
CLAUDE.md          # Claude Code
PLANS.md           # phases complexes
.gitignore
.env.example
.codex/config.toml
.claude/settings.json
.agents/skills/…/SKILL.md
Le minimum à écrire
  • README.md : objectif, installation, lancement et limites.
  • AGENTS.md / CLAUDE.md : structure, commandes, règles métier, tests et définition de « terminé ».
  • PLANS.md : étapes et critères d’acceptation d’un chantier complexe.
  • .env.example : noms des variables, jamais leurs vraies valeurs.
Gardez ces instructions courtes et concrètes. Ajoutez une règle lorsqu’une erreur se répète ; retirez celles qui ne servent plus. Si Claude et Codex sont utilisés ensemble, placez les règles communes dans un fichier partagé et faites-y référence depuis leurs fichiers respectifs.
03Donner un bon brief à l’agent

Un brief solide tient en quatre blocs. Joignez seulement les fichiers utiles et précisez lesquels font foi.

Objectif : le résultat concret attendu.
Contexte : utilisateurs, fichiers existants et fonctionnement actuel.
Contraintes : périmètre, données fictives/réelles, sécurité, mobile, outils à conserver.
Terminé quand : tests, comportement visible et livrable vérifiable.
Pour une analyse ponctuelle de documents, utilisez Claude. Pour créer ou modifier plusieurs fichiers, tester un site, automatiser un tableur et gérer Git, utilisez Claude Code ou Codex.
04Suivre une boucle qui évite les bêtises
  1. Cadrer un résultat et les données autorisées.
  2. Inspecter l’existant et les modifications non enregistrées.
  3. Planifier si plusieurs fichiers ou décisions sont concernés.
  4. Construire petit avec des données fictives, sans réécrire ce qui fonctionne.
  5. Vérifier le comportement, les erreurs, le mobile, les tests, le lint et les types.
  6. Relire le diff, commit, push, puis vérifier le résultat publié.
  7. Mesurer le temps gagné ou le risque évité avant d’élargir.
05Créer un skill seulement quand il sera réutilisé

Un skill est une recette spécialisée que l’agent peut réappliquer : par exemple « contrôler une facture fournisseur », « publier ce microsite » ou « analyser l’export caisse hebdomadaire ». Ce n’est pas un énorme prompt fourre-tout.

Un bon SKILL.md contient
  • un nom et une description qui indiquent précisément quand l’utiliser ;
  • les entrées attendues et les étapes ;
  • les contrôles et le résultat final ;
  • si utile, des scripts, références ou modèles séparés.
Règle pratique

Après deux ou trois exécutions similaires, stabilisez la méthode puis créez le skill. Pour Codex, un skill partagé au projet peut vivre dans .agents/skills/nom-du-skill/SKILL.md et être versionné avec le reste.

06Savoir ce qu’on pousse — et ce qu’on garde dehors
À versionner
  • code, tests, documentation et migrations ;
  • AGENTS.md, CLAUDE.md, plans et skills partagés ;
  • .gitignore, .env.example et configurations projet sans secret ;
  • petites données fictives nécessaires à la démonstration.
À ne jamais pousser
  • .env, clés API, jetons, mots de passe et certificats ;
  • données réelles de salariés, clients, ventes ou fournisseurs ;
  • exports lourds, caches, dépendances générées et réglages personnels ;
  • chemins locaux ou identifiants cachés dans une configuration.
Une configuration partagée doit être portable et sans secret. Pour un connecteur MCP, utilisez des variables d’environnement comme ${NOM_DE_LA_CLE}, jamais la valeur réelle dans le dépôt.
